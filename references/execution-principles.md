# AI Memory Maintenance 執行細則

**文件目的：** 補充 `SKILL.md` 在 `review` 與 `cleanup` 時需要的判斷清單。模式、作用範圍、分類、安全規則與報告格式以 `SKILL.md` 為準；兩者不一致時依 `SKILL.md`。

---

## 1. Scope 判斷補充

1. Global 層級的知識不得包含專案專屬資訊。
2. Project 層級的知識原則上必須在同一 Repository 的不同分支均成立。
3. 不得因為資訊被多個分支引用，就直接判定其為 Project 層級；仍須驗證其適用性。

## 2. 清理判斷

### 2.1 優先檢查的內容

- 重複記錄相同的技術規則。
- 已完成且沒有長期參考價值的任務過程。
- 已被新版本取代的程式碼範例。
- 已刪除或改名的 Class、Method、Table 或 API。
- 臨時除錯紀錄及錯誤堆疊。
- 沒有實際價值的對話摘要。
- 與目前專案無關的其他專案資訊。
- 已經失效的開發計畫或待辦事項。
- 缺少來源、適用範圍或上下文，且容易造成誤解的資訊。

### 2.2 不得直接清除的內容

以下資訊即使較舊，也不應直接刪除：

- 仍然有效的架構設計決策。
- 歷史相容性需求。
- 重要業務規則。
- 尚未完成的開發事項。
- 仍被其他模組依賴的技術限制。
- 已被新方案取代，但仍有必要的遷移資訊。
- 尚未確認是否失效的記憶。

### 2.3 有效性判斷原則

1. 不得單純依據檔案修改時間或記憶中記載的日期判斷記憶是否過時。
2. 優先比對目前程式碼、設定檔、資料庫結構、API 或介面定義，以及已確認的規格。
3. 必要時檢查 Git Log、Commit、Merge 狀態及分支差異。
4. 不得只根據單一檔案或單次搜尋結果，推論整個專案的實際狀態。
5. 新資訊必須有可信來源，才能取代舊資訊。
6. 新舊資訊互相矛盾時，應標記為 Conflict，保留雙方內容並要求確認；不得自行選擇一方並刪除另一方。
7. 無法確認有效性時，保留原始資訊並標記為待審查。
8. 已標記為過時或已封存的記憶不作為目前有效資訊，僅在需要歷史脈絡時查閱。

## 3. 分支相關記憶

- 不得只根據 Branch 名稱推斷實際程式碼內容。
- 分支專屬記憶應保留至確認工作已完成，且歷史資訊已妥善處理。
- 分支重新命名時，應更新記憶中記載的分支名稱，不應因此遺失記憶。
- 若分支名稱可能重複或重新建立，宜搭配 Repository 識別資訊及必要的 Commit SHA 輔助辨識。
- 記憶中記載的適用分支是歷史資訊，不應以目前分支覆蓋。
- 記憶缺少 Metadata 或分支資訊時，應先標記待審查，不得直接刪除。

## 4. 清理計畫內容

清理計畫應列出：

- 保留（Keep）
- 新增（Add）
- 更新（Update）
- 合併（Merge）
- 移動（Move）
- 封存（Archive）
- 刪除（Delete）
- 待人工確認（Needs Review）

每項異動應包含原因、來源及預期影響。

- 若無法確定目標範圍或 Repository 歸屬，不得執行修改。
- 不得將清理 Memory 擴大成未授權的程式碼重構或專案清理。

## 5. 各操作的預設行為

| 操作 | 預設行為 | 是否需要確認 |
|---|---|---|
| 分析與分類 | 自動 | 否 |
| 重複內容比對 | 自動 | 否 |
| 提出合併建議 | 自動 | 否 |
| 修正明確錯誤 | 提出計畫 | 是 |
| 移動 Memory | 提出計畫 | 是 |
| 封存 Memory | 提出計畫 | 是 |
| 刪除 Memory | 禁止直接執行 | 是 |
| 修改跨專案適用的 Memory | 提出計畫 | 是 |

## 6. 還原與追溯

- 清理前應保留可還原版本。
- 重要 Memory 的刪除應優先採用封存，而非永久刪除。
- 記錄清理時間、執行者、目標範圍及異動內容。
- 清理失敗時，不得留下半完成且無法辨識的狀態。
- 還原操作不得覆蓋清理後由使用者或其他 Agent 新增的有效內容。
